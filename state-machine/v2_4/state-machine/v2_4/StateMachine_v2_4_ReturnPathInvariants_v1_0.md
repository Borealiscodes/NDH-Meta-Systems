# ⭐ **2 — Purpose of Return‑Path Invariants**

Return‑path invariants ensure:

- governance transitions are **reversible**  
- governance transitions are **neutralizable**  
- governance transitions are **non‑absorptive**  
- governance transitions do not create **temporal load**  
- governance transitions do not create **expressive load**  
- governance transitions do not create **altitude drift**  

They are the **final safety layer** before the v2.4 machine-readable specification.

# ⭐ **3 — Return‑Path Invariant Classes**

## **RPI‑1 — Forward‑Path Invariant**
Forward transitions must be:

- linear  
- bounded  
- non‑recursive  
- non‑elevating  
- non‑absorptive  

Forward paths cannot:

- skip states  
- invert adjacency  
- elevate altitude  
- collapse expressive geometry  

## **RPI‑2 — Reverse‑Path Invariant**
Reverse transitions must:

- restore original adjacency  
- restore original temporal geometry  
- restore original expressive boundaries  
- restore original lineage position  

Reverse paths cannot:

- create drift  
- create curvature  
- create load  
- create recursion  

## **RPI‑3 — Neutral‑Path Invariant**
Neutral transitions must:

- preserve state  
- preserve adjacency  
- preserve expressive neutrality  
- preserve temporal neutrality  

Neutral paths cannot:

- accumulate metadata  
- accumulate expressive load  
- accumulate temporal load  

## **RPI‑4 — Return‑Path Symmetry**
All three paths must be:

- symmetric  
- altitude‑consistent  
- membrane‑consistent  
- lineage‑consistent  

Symmetry prevents:

- governance bias  
- adjacency bias  
- temporal bias  

## **RPI‑5 — Return‑Path Safety Envelope**
Return‑paths must remain:

- G0‑safe  
- non‑activating  
- non‑propagating  
- non‑collapsing
